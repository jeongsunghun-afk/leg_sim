Perceptive Navigation → Locomotion 파이프라인

★ 2026-07-15 검증 결론 — 험지 크로싱은 RL(하이브리드)로 피벗
③ selectFoot(로컬 footScore 발판 nudge)로 gap(0.32m갭)·stepping(0.44m간격) 완주(falls=0) 확인. 단 속도-공명 취약 — 발판간격에 정렬된 속도(이 지형=walk 0.5)에서만 성공, 0.4/0.6/0.7 실패(nudge 반경 키워도 공명이 이동만). = "발이 우연히 정렬될 때만 건넘", 지형간격 전용.
full TAMOLS→WBIC 단발 재생: 파이프라인 완성(export·C++ 추종모드)이나 추종 불안정 = 구조적 막다른길(tamols-rl은 발판1개/다리=수신horizon용, 단발 재생 부적합) → 정리.
구조 진단: 저수준(WBIC)은 문제없음. 계획층 3부재 — ①스텝길이 적응X(Raibert 고정) ②접촉 타이밍 적응X(고정 게이트 클럭=속도공명 근본원인) ③base-발판 협조 최적화X.
표준 해결: 발판+base+타이밍 co-optimization(모델기반 B2/B3=crocoddyl 실시간 OCP, quad_centroidal 참조) 또는 RL(teacher-student, 험지 SOTA). ★확정: 험지크로싱=RL(하이브리드) — WBIC·지형맵·footScore를 실행층/관측으로 재사용, A(보행·기립·점프 배포)는 모델기반 유지, ③은 경량 로컬 데모 유지. B2/B3(모델기반 OCP)는 살아있으나 현시점 미착수.
★ 2026-07-16 갱신 — 모델기반 타이밍 트랙 착수: Contact-Implicit MPC (샘플링 CI, 전략 §15 path B). 롤아웃을 MuJoCo/MJX(GPU)로 굴려 접촉 타이밍을 물리가 발견(고정 게이트 클럭 탈피) = 위 ②접촉 타이밍 적응X의 모델기반 해법. sim2sim 갭 0(배포 시뮬 그대로). 평지 전진보행 falls=0 달성, 다음=gap/stepping 크로싱. RL과 병행 — RL=험지 발판탐색 SOTA·CI-MPC=접촉모드 창발. 상세=별도 CI-MPC 파이프라인 아티팩트.

TRG-planner(Traversal Risk Graph, KAIST · 전역 경로)가 저위험·최단 경로를 내면, TAMOLS(지형인지 base+발판 최적화)가 로컬 지형에서 궤적·발판을 풀고, 하위 전신제어기(1 kHz)가 추종한다. 모든 지형 추론은 elevation map(이미 개발됨) 하나에서 나온다 — TRG의 traversal-risk와 TAMOLS의 foothold-score가 같은 맵에서 파생. ★두 관건: (1) nav↔제어는 얇은 velocity라 통합점은 perception 심(seam) 하나 · (2) 하위 제어기 TSID vs WBIC은 TAMOLS가 GRF를 정밀하게 내는지가 가른다.

SEAM 3 · 통합점 = terrain_z() 심의 확장

붙이는 곳은 이미 있는 terrain_z() 하나. 지금은 포인트 쿼리(백엔드=mj_ray)이고, 이를 레이어드 그리드맵 계약으로 넓히면 현 컨트롤러·TAMOLS·nav가 전부 같은 지점에 붙는다. 새 배선이 아니라 계약 확장.

// 백엔드 무관 계약 — sim=mj_ray / real=elevation_mapping, 인터페이스 동일
struct TerrainMap {
  double z(x, y);              // 포인트 높이 — 현 컨트롤러가 그대로 사용
  bool   valid(x, y);          // 맵 밖/구멍 → false (평지 폴백 신호)
  Submap submap(cx, cy, r);   // TAMOLS용 로컬 그리드 + 레이어
};
struct Submap { double res, ox, oy; int nx, ny;
  Grid elevation, filtered, slope, roughness, edgeSDF, footScore; };
  • 현 컨트롤러는 z()/valid()만 → 지금 Raibert·몸통높이 적응이 실맵에서 그대로 돎
  • TAMOLS는 submap()으로 그리드+레이어를 통째로 읽음
  • 파생 레이어(edgeSDF·footScore·slope)는 맵 노드에서 맵 갱신율에 1회 계산 — 1 kHz 루프 밖 (grid_map 필터 체인)

두 소비자(현 컨트롤러·TAMOLS)가 같은 계약을 공유 → nav든 planner든 붙는 곳이 하나로 수렴.

⚠ 점접촉(sphere 발) 주의: 02_Leg 발=점접촉(발바닥 패치 없음) → footScore는 "패치 밀착"이 아니라 "점 지지 안전". margin = sphere 반경 + 발배치 불확실성 σplace(σ는 sim2real latency/노이즈 발끝오차서 근거) · edgeSDF 지배(굴러떨어짐/갭 회피)·slope 보조·roughness 저비중(패치 밀착 무의미).

⚠ 게이트 무관: terrain map·footScore·TAMOLS는 발배치 층이라 walk·trot·run·stairs 전부 적용. 오히려 불연속 지형(디딤돌·계단)은 정적안정·정밀배치인 walk/stairs가 본선, trot은 완만 지형용.
