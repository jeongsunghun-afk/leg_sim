# biped 실기 사양 — RL 학습팀 인계 문서

**작성 2026-08-10.** 이 문서가 필요한 이유는 하나다:
**MJCF 모델만 넘기면 학습된 정책이 실기에서 동작하지 않는다.**
MJCF 는 4관절을 독립으로 모델링하지만 실기는 그렇지 않고, 드라이버가 각도를 잘못 보고하며,
관절한계도 MJCF 와 다르다. 아래는 그 차이의 전부다.

값의 출처를 셋으로 구분해 표기했다 — **[실측]** 실기에서 확인 · **[계산]** 다른 값에서 유도 ·
**[미확정]** 아직 근거 없음. RL 은 [미확정] 항목을 **도메인 랜덤화 대상**으로 잡는 게 안전하다.

## 0. 용어 — 각도는 네 층이다 (이 문서·코드 전체의 표준)

| 용어 | 기호 | 정의 | 감속비 | 커플링 |
|---|---|---|---|---|
| **모터축각** | `θ_m` | 실제 모터 샤프트 회전각 = **raw각** × 실제감속비. **직접 관측 불가** — 감속비 논의에서만 쓴다 | 이전 | **미해제** |
| **채널각** | `q_ch` | 드라이버가 SHM 으로 보고/수신하는 값 `= θ_m / 7` (드라이버가 전 축 7:1 로 가정) | 이전(7로만 나뉨) | 미해제 |
| **raw각** | `q_raw` | `(q_ch − offset)/(sign·k)`. 부호·감속비·영점이 제거된 값 | **이후** | **미해제** |
| **모델각** | `q_joint` | MJCF `qpos` 와 같은 관절각. 정책·GUI·뷰어가 쓰는 **유일한** 단위 | 이후 | 해제됨 |

- 커플링이 없는 축은 `raw각 == 모델각` 이다. calf·hip·thigh 가 그렇고, **foot 만 다르다.**
- **폐기된 표현**: `보고각`(→ 채널각) · `joint 각도`(→ 모델각).
- `관절각` 은 **각도 단위로 쓰지 말 것** — 어느 층인지 모호하다. 물리량 수식어로만
  쓴다(관절**토크**, 관절**한계**). 각도를 가리킬 때는 위 네 용어 중 하나를 쓴다.
- 영어가 필요하면: motor-shaft / channel / raw / model.

정책은 **모델각만** 본다. 채널각은 하드웨어 경계에서 한 번만 변환한다.

## 1. 변환 전체

### 변환 전체 (읽기: 엔코더 → 정책 관측)

```
q_raw_i    = (q_ch_i − offset_i) / (sign_i · k_i)
q_joint_i  = q_raw_i − coef_i · q_joint_(src_i)          # 커플링 있는 축만
```

### 변환 전체 (쓰기: 정책 출력 → 모터 명령)

```
q_raw_i    = q_joint_i + coef_i · q_joint_(src_i)        # 커플링 되먹임
q_ch_i     = clip( q_raw_i · sign_i · k_i + offset_i,  −180, +180 )
```

속도는 위치와 같은 선형관계(상수항 `offset` 만 빠짐).
**토크만 다르다** — `k` 로 나누고, 커플링이 **전치(transpose)** 로 들어간다:

```
τ_ch_i     = sign_i · τ_raw_i / k_i
τ_raw_src −= coef · τ_joint_dst        # 소스축(calf)이 목적축(foot) 토크를 떠안는다
```

일률 보존에서 나온다: `q_true=(I−C)q_raw` 이면 `τ_raw=(I−C)ᵀτ_true`.
각도처럼 목적축에 더하면 **틀린다** — 방향이 반대다.

구현 원본: [`emb/interface/joint_map.py`](interface/joint_map.py) ·
C++ 미러 [`cpp/src/deploy_hw.hpp`](../cpp/src/deploy_hw.hpp).
**패리티는 `cpp/tools/parity_check.py` 로 검증한다** — 관절한계 박스 전 꼭짓점(2^8=256)
+ 무작위 내부점 300개, 최대차 8.5e−6°.
⚠2026-08-10 에 실제로 어긋나 있었다: Python 에만 ±180 포화를 넣고 C++ 을 빠뜨려
  한계 꼭짓점에서 **60.09° 차이**가 났는데, 당시 확인이 **기준자세 한 점**만 봐서 통과했다.
  **한 점 검증은 패리티 검증이 아니다.** 규약을 바꾸면 반드시 이 스크립트를 돌릴 것.

## 2. ★기구 커플링 — MJCF 에 없는 가장 큰 차이

**calf(무릎)를 움직이면 foot(발목)이 종속적으로 따라 움직인다.** 발목이 링키지로 구동된다.

```
q_joint_foot = q_raw_foot  − coef · q_joint_calf
q_raw_foot   = q_joint_foot + coef · q_joint_calf
coef = +1     (HL_foot ← HL_calf,  HR_foot ← HR_calf)
```

### 반드시 짚어야 할 세 가지

**(a) coef 는 raw각·모델각 공간(= 감속비 *이후*)의 계수다** — 채널각/모터축각 공간이 아니다.
> "calf 관절이 30° 돌면 foot 관절도 30° 돈다"

⚠**부호는 [실측], 크기 1.0 은 [미확정]** 이다 — 크기의 근거는 육안 일치뿐이고
  정량 측정 기록이 저장소에 없다(§9 참조). 도메인 랜덤화 대상에서 빼지 말 것.

감속비가 다르므로(calf 10.5:1, foot 8.4:1) **채널각 비율은 1:1 이 아니다**:
`k_foot/k_calf = 1.2/1.5 = 0.8`. 실제로 calf 관절 +30° 명령 시 채널각은
**HL: calf −45° · foot −36° / HR: calf +45° · foot +36°** 로 나간다 —
다리 안에서 두 축의 **부호는 같다**(config sign 이 HL 둘 다 −1, HR 둘 다 +1).
(이 0.8 배는 모터축각으로 따져도 같다 — foot:calf = **252:315 = 0.8**.
`q_ch = θ_m/7` 로 양쪽 다 같은 7 로 나뉘므로 비에서 상쇄된다.
⚠순서를 뒤집으면 315/252 = 1.25 가 되는데, 이 값이 하필 바로 아래 과보상 배수와 같아 헷갈리기 쉽다.)

채널각 공간에 1:1 로 넣으면 `Δch_foot = Δch_calf = 45°` 가 되어 raw 보상이 **37.5°** 가 된다
— 올바른 30° 보다 **7.5° 과보상**이다(배수 `k_calf/k_foot = 1.25`).

**(b) 부호를 틀리면 상쇄가 아니라 가중된다** — `coef = −1` 로 넣었을 때 발목이 무릎을 **더** 따라갔다. **[실측]**

**(c) 이 계수는 서보가 물린 상태에서 측정할 수 없다.**
JOG 중 엔코더 회귀는 발목 모터가 **우리 보상 명령을 추종**하므로 자기 명령을 되재는 것이 된다
(결정계수가 아주 높게 나오지만 무의미하다 — 실제로 이 함정에 빠져 부호를 반대로 판정했었다.
그때의 원 로그는 남아 있지 않으므로 구체 수치는 인용하지 않는다).
기구를 재려면 **off(무여자) 상태에서 무릎을 손으로 돌려야** 한다 →
[`emb/diag/couple_check.py`](diag/couple_check.py).

### RL 이 취할 선택지

| 방법 | 내용 | 비고 |
|---|---|---|
| **A. 전동(transmission)으로 모델링** | foot 액추에이터를 `<tendon><fixed>` 에 물린다 — `foot` 계수 +1, `calf` 계수 +1 ⇒ 액추에이터 좌표가 `q_raw_foot` 이 된다 | 동역학까지 맞음. ✅**2026-08-13 채택·구현됨**(§6-d) |
| **B. 래퍼에서 변환** | MJCF 는 독립으로 두고 action/obs 래퍼에서 위 식 적용 | 기구학만 맞음. 배포 경로만 변환 |

⚠**`<equality>` 로 구속하면 안 된다.** 실제로 시뮬해 확인했다(mujoco 3.9.0):
  `equality joint1=foot joint2=calf polycoef="0 -1 0 0 0"` 를 넣으면 `neq` 0→2 가 되고
  **발목 DOF 가 제거된다**(다리당 4→3, `q_foot ≡ −q_calf` 강제).
  HL_foot 액추에이터에만 30 Nm 를 3초 주면 `foot +61.77° · calf −55.61°`(합 ≈ 0) 로
  **발목만 명령해도 무릎이 끌려간다.**
  실기는 발목 모터(`q_raw_foot`)가 **독립 좌표**라 무릎을 고정한 채 발목을 1:1 로 구동할 수 있다.
  ⇒ 커플링은 **구속이 아니라 전동**이다. equality 로 넣으면 실기와 다른 로봇이 되고,
    정책이 발목을 명령할 때마다 무릎이 딸려가 학습 자체가 무너진다.

- **sign** [실측] — 모터 + 방향이 모델좌표의 어느 쪽인가. 8축 전부 조립 후 육안 검증.
  **hip 만 좌우 같고(−1/−1), thigh·calf·foot 은 모두 좌우 반대다**(foot 은 −1/+1). 위 표 참조.
- **offset** [실측] — **채널각 단위**다(`sign·k` 로 나누기 **전에** 뺀다). 기준자세에서 채취.
- **gear_k** [계산+실측] — 드라이버 감속비 오설정 보정. 아래 §4.
- **질량 좌우 비대칭** — MJCF hip 질량이 HL 1.3 kg vs HR **1.4 kg (7.7% 차)**. 총질량 13.5707 kg.
  torso 3.0 kg 은 quad 절단 후 넣은 **플레이스홀더**이고 실기 대조를 한 적이 없다.
- **`tau_peak` 은 순환일 여지가 있다** — 84/84/126/100.8 Nm 는 MJCF `jnt_actfrcrange` 가 유일
  출처인데, 8축 모두 `tau_peak ÷ gear = 12.0 Nm` 로 데이터시트와 정확히 일치한다.
  애초에 `12 × N` 으로 만든 값일 수 있다. calf/foot 모터 라벨을 눈으로 확인하면 확정된다.
- **kp/kd** — 드라이버 MIT 임피던스 게인. **단위가 rad 기준**이다: `τ = kp·(q_des−q)[rad] + kd·(dq_des−dq)[rad/s]`.
  명령·상태는 deg 인데 게인은 rad 라 `kp 1 ≈ 0.0175 Nm/deg`. [실측: 예측 0.775 Nm vs 실측 0.757 Nm, 오차 2%]

## 4. 드라이버 감속비 오설정 — 각도 배율이 축마다 다르다

드라이버가 **전 축을 7:1 로 가정**해 관절각을 보고한다. 실제 감속비는 hip/thigh 7 · calf 10.5 · foot 8.4.

```
보고각 = 실제 관절각 × (실제감속비 / 7)      →  gear_k = 실제감속비/7
gear_k: hip 1.0 · thigh 1.0 · calf 1.5 · foot 1.2
```

**[실측]** `gear_k` 적용 후 뷰어와 실기의 회전비율이 일치함을 확인.
이 관찰은 **링키지 가설을 배제한다** — 4절 링키지라면 배율이 자세마다 변해 **상수** `k` 로는
전 구간이 맞을 수 없다. 상수 하나로 맞았다는 것이 "드라이버가 고정 7:1 로 나눈다"의 서명이다.

### RL 이 알아야 할 파급

**게인이 설계보다 세게 걸린다.** 드라이버는 채널각 오차에 kp 를 곱하는데,
채널오차 = 배율×관절오차이고 실제토크 = 보고토크×배율이므로

```
실제 관절강성 = kp × k²
calf 50 → 실효 112.5 (2.25배)   ·   foot 30 → 43.2 (1.44배)
감쇠비도 ζ×k 로 변한다: calf 0.76→1.13(과감쇠) · foot 0.82→0.97
```

⚠**드라이버가 고쳐지면 calf·foot 이 갑자기 약해진다.** RL 정책이 이 강성에 의존해 학습됐다면
그때 재학습이 필요하다. 그 전까지는 `gear_k` 를 그대로 두는 게 실기와 일치한다.

**토크 임계의 의미도 축마다 다르다.** `safety.tau_trip_nm` 은 **보고토크** 기준이라
설정 15 Nm 이 calf 는 실제 22.5 Nm, foot 은 18 Nm 이다. **[미해결 — 균일화 안 함]**

## 5. 한계는 **박스가 아니다**

커플링 때문에 `(calf, foot)` 의 허용 영역이 직사각형이 아니다. 세 층이 있다:

1. **관절한계** `min/max_deg` — 모델각 공간, 축별 독립. 위 표.
2. **raw각 제약** — 물리 제약은 발목 **raw각**(`q_raw = foot + coef·calf`)에 걸린다.
   foot 단독으로 좁히면 무릎이 펴져 있을 때 쓸 범위까지 잘린다.
3. **★±180 래핑** — Emb 는 초과분을 클램프가 아니라 **래핑한다**
   (`halGait.cpp:666-671`, `while(fPosition>180) fPosition-=360`).
   181° 를 보내면 −179° 로 뒤집혀 **반대편으로 날아간다.**
   ⇒ 우리 코드가 `q_joint_to_ch` 에서 ±180 으로 **포화**시켜 막는다.
   현재 관절한계 끝단에서 최대 |ch|: HR_thigh 169.4 · HR_calf 174.7 · foot 180.0(극단 조합에서만).

**RL 이 액션 범위를 정할 때** 1번(관절한계)만 보면 안 되고, 2·3 을 위반하는 조합은
포화되어 **명령이 조용히 왜곡된다**. 포화 횟수는 `JointMap.n_saturated` 로 노출돼 있다.

## 6. MJCF ↔ 실기 불일치 — 전이 실패의 후보 (코드 전수조사 결과)

### 6-a. ★MJCF 만 로드하면 **이상적인 로봇**이 나온다
MJCF 에 `armature` · `damping` · `frictionloss` 가 **한 줄도 없다**(전수 grep 0건).
컴파일하면 14 dof 전부 정확히 0.0 이고, 실측값은 **컨트롤러가 런타임에 주입**한다:

| 항목 | 값 | 출처 |
|---|---|---|
| `armature` (= ROTOR_I·N²) | hip·thigh 0.0363 · calf 0.0816 · foot 0.0522 kg·m² | ROTOR_I 7.4e−4 [실측, hip 2축만] |
| `damping` (JDAMP) | 0.09 N·m·s/rad | [실측, hip 2축만] |
| `frictionloss` (JFRIC) | 0.38 Nm | [실측, hip 2축만] |

**RL 이 MJCF 를 그대로 쓰면 반사관성·마찰이 0 인 로봇을 학습한다.** 반드시 주입할 것.

★**발목·무릎은 링크가 아니라 기어박스가 지배한다** — 등가관성 중 로터 반사관성 비중:
  hip 18.6% · thigh 23.3% · **calf 73.9% · foot 96.3%**
  (I_link: hip 1.5887e−1 · thigh 1.1941e−1 · calf 2.8798e−2 · foot 2.0175e−3 kg·m²)
  armature 를 빠뜨린 모델에서 이 두 축은 **질적으로 다르게(훨씬 가볍고 빠르게)** 움직인다.
  발목 whip 억제·착지 임팩트 학습이 전혀 전이되지 않는다.
⚠thigh/calf/foot 의 JDAMP·JFRIC 는 **hip 값을 외삽**한 것이다 — 축별 실측이 없다.
⚠반사관성은 무해하지 않다: ROTOR_I 스윕에서 1e−4~5e−4 는 15s 무낙상, 실측 7.4e−4 는
  **2.18s 낙상**했다. 원인은 스윙 가속 토크가 tau_peak 을 넘어 QP 포화. 해법은 게인이
  아니라 **스텝시간**이었다(SW_KP 를 7배 올려도 악화, T_STEP 을 늘려야 해결).

### 6-b. ✅관절한계 — **CAD URDF 로 통일됨** (2026-08-11)

| 축 | 종전 MJCF | **새 CAD** | 방향 |
|---|---|---|---|
| hip | −35.0~35.0 | **−14.9~14.9** | 좁아짐(안전) |
| thigh | −135.0~65.0 | **−64.7~135.2** | ★+쪽 70° **넓어짐** |
| calf | −62.0~65.0 | **−59.6~49.8** | 좁아짐 |
| foot | −80.0~62.0 | **−84.8~25.2** | +쪽 좁아짐, −쪽 4.8° 넓어짐 |

⚠**thigh(+70°)·foot(−4.8°) 는 넓어지는 방향**이다. URDF 가 틀렸다면 하드스톱에 부딪힌다.

⚠운동학(관절 원점·축)은 hip x 오프셋과 발끝 접촉점을 빼면 종전과 **완전히 동일**하다.

### 6-d. ✅커플링이 바꾸는 **토크 실현가능집합** — **모델에 반영됨** (2026-08-13)
§2 의 전치 관계 때문에 실제 낼 수 있는 토크 집합은 독립 박스가 아니라 **전단된 집합**이다:

```
  드라이브 토크   u_calf = τ_calf − τ_foot   (|·| ≤ 126)
                  u_foot = τ_foot            (|·| ≤ 100.8)
```

무릎·발목 토크의 **부호가 반대면** 무릎 드라이브 부하가 합쳐져 여유가 줄고(τ_foot=−100.8 이면
τ_calf 는 +25.2 까지), **같은 부호면 오히려 넓어진다**(발목 반력이 무릎을 도와 +226.8 까지).
⚠종전 서술 "발목에 큰 토크를 쓰면 무릎 여유가 그만큼 준다" 는 **절반만 맞다** — 방향에 따라 갈린다.

**MJCF·컨트롤러 반영 (2026-08-13):**
- 발목 액추에이터를 `<motor tendon="*_foot_rotor">` 로 옮겼다 ⇒ `d.ctrl` 이 **드라이브 토크**다.
- WBIC QP 의 토크한계 부등식과 최종 클립을 **드라이브 공간**으로 옮겼다(calf 행만 전단).
- 상수 개명 `tau_peak`→`drv_peak`(C++ `drv_peak8` · Python `DRV_PEAK`). 의미가 관절→드라이브로
  바뀌어서다. calf **관절**의 `actuatorfrcrange` 는 두 드라이브 합 **±226.8** 로 넓혔다.
- 회귀(`cpp/verify.sh` 6조건): 전 항목 통과. 비포화 구간은 종전과 **수치까지 동일**하고
  v0.15 만 tilt 1.4→1.3° · x +9mm — 예상대로 **포화 순간에만** 갈린다.

### 6-d2. ★접촉 모델의 함정
- ⚠**`condim` 은 3 이다. 6 으로 올렸다가 되돌렸다** (2026-08-13). 미해결 항목으로 남는다.
  올리려던 이유는 여전히 유효하다 — condim 3 은 미끄럼 마찰만 쓰므로 `friction` 의
  비틀림(0.05)·구름(0.001) 항이 **무시된다**.
  되돌린 이유: **WBIC 가 접촉을 3-DOF 점힘으로 푼다**(`cjac` 3×nv · λ 3벡터).
  condim 4/6 은 제어기가 모르는 접촉 **모멘트**를 물리에만 추가해 모델이 어긋난다.
  평발 2점 stand 15초 실측(Qflat8 재산출 후):

  | condim | 결과 | tilt | base z |
  |---:|---|---:|---:|
  | **3** | 무낙상 | 0.2° | 0.438 |
  | 4 | 무낙상 | 2.0° | 0.403 (**3.5cm 침하**) |
  | 6 | **8.08s 낙상** | — | 붕괴(접촉 4→2) |

  ⇒ 올리려면 **WBIC 접촉모델의 6-DOF 확장이 선행**이다. 물리만 올리면 손해다.
  ★**RL 은 다르다** — 학습은 주어진 접촉모델에 맞춰 배우므로 condim 6 으로 학습해도 된다.
    오히려 yaw 저항이 있는 쪽이 실기에 가깝다. 단 그렇게 학습한 정책은 이 WBIC 와
    **같은 접촉 가정 위에 있지 않다.**
  ⚠"발이 자유롭게 헛돈다" 는 **1점 점발 모델의 문제**다. 평발판은 발당 접촉구가 2개라
    condim 3 에서도 두 점의 차동 마찰로 yaw 를 버틴다 — 실기 밑창에 가까운 건 그쪽이다.
- **`solref="0.004 1"` 은 timestep 0.002 의 정확히 2배** = 접촉 강성 한계선이다.
  RL 이 속도를 위해 timestep 을 늘리면 **접촉이 폭발**한다. 늘리려면 solref 도 같이 볼 것.
  ⚠condim 6 은 접촉당 구속 차원을 늘리므로 이 여유 없는 지점이 **더 얇아졌다**.
- 발 sphere 외에 **다리 링크 메시도 충돌체다**(`contype` 미지정 = 1). 평발 홈자세에서
  `HL_foot_link` 메시 최저점 z = 0.0111 m, `HL_calf` z = 0.0106 m — 지면과 1 cm 여유뿐이라
  실제로 닿을 수 있다. 두 MJCF 는 여기서도 다르다(평발판은 다리 메시 8개를 전부 `contype=0`).

### 6-d2. ★접촉 모델의 함정 두 가지
- **`condim=3` 이라 지정된 비틀림·구름 마찰이 무시된다.** geom 에 `friction="1.6 0.05 0.001"`
  이라 써 있지만 condim 3 은 **미끄럼 마찰만** 쓴다 ⇒ 발이 수직축으로 **자유롭게 헛돈다.**
  실제 밑창의 yaw 저항이 시뮬에 0 이므로 **선회·요 안정화 정책이 과대평가**된다.
- **`solref="0.004 1"` 은 timestep 0.002 의 정확히 2배** = 접촉 강성 한계선이다.
  RL 이 속도를 위해 timestep 을 늘리면 **접촉이 폭발**한다. 늘리려면 solref 도 같이 볼 것.
- 발 sphere 외에 **다리 링크 메시도 충돌체다**(`contype` 미지정 = 1). 평발 홈자세에서
  `HL_foot_link` 메시 최저점 z = 0.0111 m, `HL_calf` z = 0.0106 m — 지면과 1 cm 여유뿐이라
  실제로 닿을 수 있다. 두 MJCF 는 여기서도 다르다(평발판은 다리 메시 8개를 전부 `contype=0`).

### 6-h. 구조 차이
- **base**: MJCF 는 freejoint(torso z=0.52). 실기는 현재 **크레인 거치(공중 매달림)** 이고
  off/jog/home/hold 4모드만 허용된다.
- ✅**torso 충돌 ON** (2026-08-13). 종전엔 `contype=0` 이라 몸통이 지면을 통과해 넘어짐을
  학습·평가할 수 없었다. ⚠비트마스크로 **바닥하고만** 부딪히게 했다(torso 2,2 · floor 3,3) —
  기본값을 주면 점발판에서 torso↔대퇴 자기충돌까지 새로 생긴다. `density=0` 유지(질량 불변).
  회귀 영향 **0**(6조건 전부 소수점까지 동일) — 보행 중엔 안 닿기 때문이다.
  다리 링크 메시는 충돌 ON 이고 발 sphere 와 접촉 파라미터가 다르다(friction 1.3 vs 1.6,
  solref 0.02 vs 0.004 = **발의 5배 물렁**).
- **허리 2축**: 실기에 물리적으로 있으나(SHM 채널 8·9) MJCF 에 **없다**. 0° 고정 홀드.
- **quad 잔재**: 모델명 `biped_from_quad_17dof_hind`, `meshdir=../quad/meshes_sim_17dof/`
  (STL 이 `biped/` **밖에** 있다 — 인계 시 함께 보낼 것). 관절명 HL/HR = Hind Left/Right.
- **MJCF 두 벌**: 점발(`biped_from_quad`, 배포) · 평발(`biped_flatfoot`). 차이는 접촉 geom 뿐이라

`mpc_decim` 이 따라 계산되므로 MPC 는 50Hz 로 유지된다.

### ⚠이름 함정: "Emb" 가 두 개다
우리 디렉터리 `emb/` 와 벤더 프로세스 `RobotEmbedded` 가 둘 다 "Emb" 로 불린다.
**500Hz 는 우리 제어기**, **1kHz 는 RobotEmbedded** 다. 문서·대화에서 반드시 구분할 것.

### 정책 추론 주기를 정할 때 참고값
| 주기 | 조건 |
|---|---|
| **50 Hz** | 정책이 목표(속도·자세)를 내고 하위 제어기가 추종 — 기존 MPC 자리 |
| **500 Hz** | 정책이 **관절토크를 직접** 낸다 — 기존 WBIC 자리 |
| **1 kHz** | Emb 와 1:1. Python 으로는 불가 → C++ 경로(`cpp/src/biped_deploy.cpp`) |

### ★SHM 은 스트림이 아니라 **버퍼**다 — 주기 불일치로 손실이 생긴다
| 방향 | 비율 | 결과 |
|---|---|---|
| 제어기 500Hz 쓰기 → Emb 1kHz 읽기 | 1:2 | Emb 가 **같은 명령을 평균 2번** 실행 |
| Emb 1kHz 갱신 → 제어기 500Hz 읽기 | 2:1 | **상태 샘플 절반을 버린다**(에일리어싱) |

jog/hold 같은 느린 동작엔 무해하다. 그러나 **속도 미분이 절반 샘플만 보고**,
500Hz 를 넘는 제어 대역은 원리적으로 낼 수 없다. 고대역 토크 정책이면
`ctrl_hz` 를 1000 으로 올려 1:1 로 맞춰야 하고, 그러면 Python 은 불가하다
(현재 500Hz 에서 루프 주기 p95 2.5ms — 1kHz 목표 1.0ms 에 여유가 없다).

### 파이프라인 실측 (2026-08-10)
```
GUI ──cmd.json ~10Hz(설정 20Hz)──> 제어기 ──SHM 500Hz──> RobotEmbedded ──EtherCAT 1kHz──> MCU ──> 로봇
                                     └──state.json 50Hz──> 뷰어 · GUI 표시
```
- 제어기 루프 실측: p50 1.999 · p95 2.50 · max 7.9 ms · 평균 500.0 Hz
- `state age`(뷰어 HUD)는 **주기가 아니라 신선도**[ms]다. 톱니 꼭대기 ≈ 발행주기.
  피드가 끊기면 단조 증가해 `*** STALE ***` 이 뜬다 — Hz 지표는 얼어붙어 못 잡는다.

### ⚠현재 MPC/WBIC 은 **돌지 않는다**
제어기는 `stand`/`walk` 를 진입에서 거부한다(`biped_emb.py:374`). jog/home/hold 만 처리한다.
모델기반 실기 배포는 `cpp/build/biped_deploy` 담당인데 **아직 실기에서 한 번도 돌린 적이 없다.**
이 문서의 영점·감속비·커플링 검증은 전부 jog/home/hold 경로에서 이뤄진 것이고,
**모델기반 경로(토크 제어)는 미검증**이다.

## 8. 붙는 지점 (인터페이스)

- **관측**: `/tmp/biped_state.json` — `q_leg_deg`(**모델각**, 커플링 풀린 값) ·
  `q_ch_deg`(**채널각**, 캘리브레이션용) · `rpy_deg`(IMU, 현재 0) · `health`/`installed` · `loop_hz`
- **명령**: `/tmp/biped_cmd.json` — `mode` · `jog_deg`(모델각) · `v`/`vy`/`w` · `body_h` · `contact` · `seq`
  - ★**폴링이 50Hz 다** — 500Hz 루프여도 외부 명령 반영률의 상한은 50Hz(20ms ZOH). 파일 채널로
    500Hz 정책을 배포하면 액션이 10틱씩 유지된다.
  - ★**`seq` 를 반드시 증가시킬 것.** 워치독이 "내용이 바뀌었는가" 로 생존을 판정하므로
    같은 액션을 두 번 쓰면 두절로 간주된다(500ms → limp).
- **저수준**: `emb/interface/hw_interface.py` 의 `write_jog` / `write_hold` / `write_torque`.
  **토크 제어는 `write_torque(q_rad, dq_rad, tau_nm, kp=0, kd=0)`** — RL 이 붙을 가능성이 가장 높은 지점.
- 파일 기반 IPC 는 상태 50Hz · 명령 ~10Hz 다(§7). 고주파 정책이면 SHM 에 직접 붙을 것.

### ✅ 순수 토크모드 — 실기 확인됨 (2026-08-11)

**`fTorque` 가 실제로 쓰인다.** HL_foot 에 `Kp=Kd=0` 으로 두고 τ_ff 만 올려
양방향 4회 전부 파단(breakaway)이 났다.

| 방향 | 파단 τ [Nm 채널] | 관절(τ_ch·k) |
|---|---:|---:|
| + | 0.740 · 0.548 | 0.888 · 0.658 |
| − | 0.629 · 0.779 | 0.755 · 0.935 |
| **평균** | **0.674 ± 0.105** | **0.809** |

교차검증 — 8축이 같은 모터(RO100)라 **모터축**으로 환산해 비교한다:

| 축 | 관절 τ_s | N | 모터축 τ_s |
|---|---:|---:|---:|
| hip (위치모드, 다리 미장착) | 0.63~0.71 | 7.0 | 0.0900~0.1014 |
| **foot (τ_ff, 다리 장착)** | **0.809** | 8.4 | **0.0963** |

전혀 다른 측정법·축·기어·다리 유무인데 **모터축 마찰이 hip 중앙값 대비 +0.6%** 다
⇒ 마찰이 모터/드라이버에서 오지 기어박스나 링크에서 오는 게 아니다.
⚠단 산포가 ±0.015 라 [0.081, 0.111] 이고, 기어보정 안 한 값 0.0802 도 hip 구간 바로
  아래다. **이 데이터만으로 `gear_k` 를 검증했다고는 못 한다** — 반복 측정이 필요하다.

#### ★순환 문제에 대한 결론 — 구조적으로는 해소, 스케일은 미해결

| | 위치처프 (종전) | **τ_ff (지금)** |
|---|---|---|
| 입력 | q_des (우리) | **τ_ff (우리, 정확히 앎)** |
| 드라이버가 돌려주는 τ | `kp·err + kd·derr` 로 **R² 0.97 재구성** | kp=kd=0 이라 재구성할 항이 없다 |
| 회귀가 식별하는 것 | **우리 게인의 그림자** | 실제 플랜트 |
| 출력 | q (엔코더, 독립) | q (엔코더, 독립) |

⇒ **τ_ff 로 도는 시험에 한해 순환은 원천 소멸한다.** 입력이 우리 것이고 출력이
독립 센서다. `fTorque` 를 회귀에 쓰지 않는다(쓸 필요도 없다 — 명령값이 곧 입력).

⚠**그러나 토크 "스케일" 은 여전히 미검증이다.** 확인한 것은 τ_ff 가 **쓰인다**는 것이지,
  0.674 를 명령했을 때 실제로 0.674 Nm 이 나온다는 것이 아니다. 드라이버의 `kt`·
  감속비 오설정·전류루프 오차가 전부 τ 에 **배율 α** 로 실린다.
  관성은 `I = dτ/dq̈` 이므로 **α 가 그대로 I 에 곱해진다.**
  `fCurrent` 가 `fTorque` 복제라 독립 검증 수단이 없다(§9 표).
  ⇒ 확인 경로는 셋: ① 파단토크↔위치모드 정지마찰 대조(위, 약한 지지)
    ② 식별 `I_joint` ↔ MJCF 예측 대조  ③ RGA 에 진짜 Iq 노출 요청

#### ✅2026-08-11 결과 — `ROTOR_I` 독립 검증 + 강한 Stribeck
지렛대 확장(6준위 · 이동 70° · 반복 2회 · **q̈~τ 회귀**) 후 foot 좌우:
`I_joint` **0.05166 / 0.05598** (예측 0.054339 대비 −4.9% / +3.0%, 평균 **−1.0%**).
한쪽은 −, 한쪽은 + 로 예측을 **감싼다** ⇒ 계통오차가 아니라 산포다.
⇒ `ROTOR_I` = 7.327e−4 로 종전 7.4e−4 와 1% 일치 — **순환 없는 경로의 독립 검증**이다.
⚠초기 −13%/−19% 는 물리가 아니라 설계 결함이었다(회귀 방향 τ~q̈ · 준위 4개 · 이동 27°).

**강한 Stribeck**: q̇=100dps 운동마찰이 정지마찰의 **57~63%**
(τ축 절편 0.474/0.421 vs 파단 0.708/0.686). MJCF `frictionloss` 는 상수라 표현 못 한다
→ 도메인 랜덤화 후보. q̇_ref 를 훑으면 이 시험이 그대로 마찰-속도 곡선계가 된다.

### 계획된 측정 (`emb/NEXT_HW.md`)
`--tests inertia`(2단 토크법)로 `I_total` 을 τ_ff 경로에서 재고, MJCF 예측과 대조한다.
이게 끝나면 위 표의 `JDAMP`·`JFRIC`·`ROTOR_I`(타축 가정)가 해소된다.
⚠측정 자세는 기준자세로 고정해야 한다 — hip `I_link` 는 무릎 −40° 에서 **+15%** 변한다.

**`coef` 와 `gear_k` 둘 다 유효한 정량 측정이 없다.** 확인된 것은 육안 일치뿐이다.

⚠**철회**: 이전에 "실효비 0.947, 5% 오차" 라고 적었으나 **그 측정은 무효다.**
JOG 중 채널각 회귀로 얻은 값인데, JOG 에서는 발목 모터가 우리 보상 명령을 추종하므로
회귀가 잰 것은 기구가 아니라 **우리 자신의 명령**이었다(0.8 에서 벗어난 4.7% 는
물리 파라미터가 아니라 서보 추종지연이다). 지금까지 나온 어떤 숫자도 5% 불일치의
근거가 되지 못한다.

⇒ 분리하려면 **두 측정이 모두** 필요하다:
  1. `coef` — off(무여자)로 두고 무릎을 손으로 돌려 `diag/couple_check.py`
  2. `gear_k` — 각도기로 `diag/chain_check.py --axis N --physical`, **두 자세 이상**
  한쪽만 재면 오차가 어느 파라미터 것인지 여전히 갈리지 않는다.
