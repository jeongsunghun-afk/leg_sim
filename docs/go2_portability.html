Go2 이식으로 본 제어기 — 무엇이 되고 무엇이 안 되나

"우리 로봇(02_Leg)이 문제인가, 접근법이 문제인가"를 가리려 제어기를 Unitree Go2(12-DOF·점발·15kg)에 이식했다. 그 과정에서 숨은 버그 3개를 잡았고, 무엇이 로봇 특유였고 무엇이 근본 한계인지가 갈렸다.

대상 02_Leg(17-DOF) ↔ Go2(12-DOF) 스택 MPC + WBC(TSID/HQP) + TAMOLS 커밋 cea6632 · c4c1722 · ea3d9d0 · e5e80e7 상태 평지 검증 · 험지 미해결

한 줄 결론

로봇은 병목이 아니다. A제어기가 Go2를 전속도 완주하고, TAMOLS도 버그를 고치니 걷는다. solve_fast에서 정식화 버그 4개(base-z·y_min·HQP·walk-CoM)를 찾아 고쳤고 진단은 매번 맞았다. 그런데 계단 실험이 최종 판정을 내린다: A(Raibert+footScore)는 계단을 오르고(02_Leg 0.48m 완주) TAMOLS solve_fast는 0계단. → TAMOLS는 평지도 A만 못하고(발판 뭉침) 험지도 완패 = 존재 이유 없음. solve_fast는 폐기하고 A+footScore가 배포 험지, TAMOLS는 DTC(RL 레퍼런스)로 자리를 옮긴다.

아키텍처평지 보행험지(경사·계단·갭)
① TAMOLS + WBC (MPC 없음) ✓ TSID V≤0.6✗ 못 넘음
② 예측 OCP + WBC (B/C·OCS2·crocoddyl) — 미검증✗ (CI-MPC 종결)
③ SRBD-MPC + WBIC (= A제어기, MIT식) ✓ Go2 V≤2.5✗ (모델기반 한계)

→ 평지는 ①·③ 둘 다 된다. 험지는 ①·②·③(모델기반) 모두 한계 → RL 피벗. D1도 동일 경로(② OCS2 → RL/HIMLoco).

01왜 Go2로 옮겼나

02_Leg에서 full-TAMOLS+WBC가 "서기만 하고 못 걷는다"는 현상이 로봇 특유(marginal·leg-heavy·허리·발목)인지, 접근법 자체인지 구분이 안 됐다. Go2는 SRBD 가정에 이상적인 로봇(점발·경량 다리·단일 트렁크·12-DOF)이라, 같은 제어기를 얹어 로봇 변수를 통제하면 원인이 갈린다.

이식 자체는 이름 규약 리네임(RL→HL 등)·모델 자동감지로 해결. MPC 질량·관성은 모델에서 자동 계산(TOTAL_MASS=body_subtreemass[0])이라 로봇 무관하게 적응.

03찾아 고친 버그 3개 (+되돌린 1개)

"접근법 한계"로 보이던 것들의 정체. 모두 진단(계획 덤프·gdb·발판 측정)으로 규명.

BUG 1계획 base 높이가 로봇에 안 맞음 FIXED

TAMOLS 플래너에 넘기는 base z가 0.52(02_Leg값)로 하드코딩. Go2(다리 한계 0.42)엔 물리적으로 불가능한 높이로 서라고 명령 → 매 스텝 위로 뻗다 붕괴. TAM_DUMP로 계획을 덤프해 규명(계획 z=0.52).

수정 tam_z0 = base_z0 → 계획 z 0.52→0.30. 결과: ① pure TAMOLS+WBC가 Go2서 걷기 시작(V≤0.3), injection V≤0.6.

BUG 2strict HQP heap 크래시 (저-DOF) FIXED

Go2 HQP가 V≥0.25서 SIGABRT(heap corruption). gdb 백트레이스 → eiquadprog reset의 malloc에서 감지. 근본: Go2는 관절 12개(nv=18)뿐이라 swing 다리 ≥3인 위상서 strict L2 등식(6+3·nsw+base)이 변수 수를 초과 → 솔버 버퍼 오버런. (02_Leg는 nv=23이라 여유.)

수정 over-determination 가드(등식≥변수면 base-L1 강등→stance 폴백). HQP도 Go2 평지 보행 가능(V≤0.2).

BUG 3발판 좌우폭 하드코딩 → 발판 뭉침 FIXED

뷰어서 "앞다리-뒷다리 거리가 너무 좁다"는 관찰에서 출발. solve_fast의 foot_y 제약 y_min=0.10이 02_Leg값이라, Go2(hip폭 0.093)엔 발을 과하게 넓게 강제 → 전체 최적해를 왜곡해 앞뒤 간격까지 뭉침.

지표수정 전수정 후정상(hip)
앞뒤 wheelbase0.0360.244 ↑0.387

보행 tilt (V=0.3)7.4°1.7° ↓—

수정 y_min/y_max를 로봇 hip 폭에서 계산. 좌우 과폭이 앞뒤까지 뭉치게 한 커플링 해소 → 보행 tilt 대폭 감소.

되돌림leg-order 순열 — 시도했다 revert

플래너는 발 순서를 [FL,FR,RL,RR], 컨트롤러는 [HL,HR,FL,FR]로 가정. 순열로 맞추려 했으나 02_Leg를 깨뜨려 되돌림 — 원 코드가 이미 자기-정합적(각 슬롯이 같은 다리에 앵커·적용)이었음. 발판 뭉침의 원인은 leg-order가 아니라 위 BUG 3(y_min)이었다.

04HQP vs TSID — 저-DOF 로봇의 반전

논문 표준은 TAMOLS + HQP(strict null-space)지만, 우리가 실제로 Go2를 걷게 한 건 TSID(weighted WBC)였다. HQP(strict)는 Go2의 낮은 DOF(12관절)에서 strict cascade의 여유가 부족해 상한이 낮고(V≤0.2), 특정 위상서 over-determination 크래시까지 났다.

교훈저-DOF 로봇엔 TSID(weighted)가 HQP(strict)보다 강건하다. strict 우선순위는 여유(redundancy)를 요구하는데 12관절은 부족 → soft trade-off인 TSID가 우세. 논문 표준이 항상 우리 로봇에 최적은 아니다.

05험지 = 안 된다 (그리고 발판폭은 답이 아니다)

평지 성공과 달리, 험지 통과는 로봇을 바꿔도 안 된다. Go2(이상적 SRBD 로봇)도 3cm 계단·10° 경사에서 넘어진다. 평지 개선(base-z·발판폭)이 험지엔 전이되지 않는다.

"발판을 넓히면 더 안정 아닌가?" — 절반만 맞다

사용자 가설을 직접 검증. 발판폭(wheelbase)을 스윕하며 평지 안정성 + 경사 등반을 측정.

발판폭 (SWX)평지 V=0.3경사(10° 램프, x1.0–2.96)
1.0× (기본)falls 0 · tilt 1.7°x=1.29 오르다 붕괴
1.5× (넓게)falls 0 · tilt 2.2°안 넘어짐 · x=0.99 정체
2.0× (과폭)—붕괴 (수직력↓)
발판폭의 정체 넓은 발판 = 더 안정(안 넘어짐) ✓ — 사용자 직관은 맞다. 단 2.0×는 과함(뒤집힌 U자). 그러나 험지 통과엔 무이득: 셋 다 램프를 못 오른다(성공=x>2.9). 넓은 발판은 "붕괴"를 "안정한 정체"로 바꿀 뿐, 올라가진 못한다. 발판폭은 안정성 레버이지 추진 레버가 아니다.

왜 못 오르나 — 진짜 병목

참조추종을 계측(TAM_TRK)하니 경사에서: 발이 경사면 접촉을 잃고(nst 4→1→0) → 명령 GRF를 실제로 못 냄 → base pitch가 제어 불가로 폭주(+56°). 그리고 계획(TAMOLS)이 base를 경사에 맞춰 pitch하지 않는다(15° 경사에 계획 pitch ~4°). 즉 발판+base 협조가 계획엔 약하게만 있고, 순간 WBC가 접촉 전이를 예측 못 해 실행이 무너진다.

06돌파구 — solve_fast를 버리고 Raibert + footScore

발판이 뭉치는 근본은 solve_fast가 발판을 통째로 최적화하는데 그 품질이 나쁘다는 것. 발상 전환: 발판 기본값 = Raibert(hip 기준, 자연히 벌어짐·안정 — A제어기가 이미 검증)로 두고, TAMOLS/지형은 "안전한 셀로 nudge"하는 보정만 맡긴다. solve_fast 발판을 아예 안 쓰니 뭉침·충돌이 사라진다. 이게 코드의 FOOT_NUDGE(③selectFoot: Raibert 발타깃 → 반경내 footScore 최고셀로 당김).

테스트발판 소스결과
02_Leg 스테핑(discrete 발판)Raibert + footScore nudge (walk)✓ 완주 falls=0 (x=7.0)
02_Leg 스테핑solve_fast(MODE=tamols)✗ 뭉침·불안정
Raibert + solve_fast 편차(INJECT)혼합— 평지서도 A 악화(오염)
검증됨Raibert + footScore(selectFoot)가 solve_fast 없이 스테핑을 완주한다. "기본 Raibert가 발판을 잡고, 지형은 nudge만" — 이 아키텍처가 solve_fast의 뭉침·충돌을 원천 제거한다.
단, 결정적 구분 selectFoot = 발판 "배치(placement)" 해결이지 "등반(climbing)" 해결이 아니다. 스테핑·갭(같은 높이 discrete 발판)은 footScore로 건너지만, 경사·오르막 계단(올라가는 지형)은 수직 추진이 필요 → 발판폭·발판선택 어느 것도 못 푼다. 앞의 Go2 경사/계단 실패는 배치가 아니라 등반 문제. 두 축은 직교한다.

07계단 판정 — TAMOLS vs A

TAMOLS의 존재 이유 = 험지에서 A보다 나아야 함(평지는 떨어져도 됨). 계단으로 직접 판정:

계단 (얼마나 높이 오르나)A (Raibert+footScore+walk)TAMOLS (solve_fast)
Go23계단 (0.12m)0계단
02_Leg16계단 = 0.48m 완주0계단
판정solve_fast 정식화 버그 4개(base-z·y_min·HQP·walk-CoM)를 다 고쳐도 계단 0 = A에 완패. 평지도 A만 못하고(발판 뭉침) 험지도 못 이긴다 → 존재 이유 없음. solve_fast는 Gauss-Newton SQP로 구조는 건전하나, cost/constraint 정식화가 계통적으로 약하다(nominal 약함·GIAC slack 느슨·CoM centering 부재).

08결론 & 다음

  • 로봇 모델은 병목이 아니다. A제어기가 Go2 완주. 02_Leg 난점 상당부분은 로봇 특유.
  • "TAMOLS는 서기만 한다"는 오판이었다. 정식화 버그 4개가 원인, 진단은 매번 맞았다(walk-CoM은 "플래너가 walk에 맞춰 gait 생성해야"라는 사용자 진단 → 지지발 centroid 추종 비용으로 해결).
  • 그래도 A를 못 이긴다. A+footScore(selectFoot)가 배치 험지(스테핑·계단)를 실제로 건넌다 — solve_fast 없이.
  • 험지 = 직교 2축: 배치(스테핑·갭 → selectFoot)와 등반(경사·계단 높이 ~0.06m 벽 → 추진/base-pitch, 미해결).
  • TAMOLS는 폐기가 아니라 이사. solve_fast(발판 플래너)는 배포서 A+footScore로 대체하되, TAMOLS TO는 DTC(RL 레퍼런스)로 재사용.
DTC 방향DTC(TAMOLS TO → RL)에선 base-z·실행은 RL/WBC가 담당(TO는 참조만) → TO는 실행가능성 부담 없음. 정밀 험지(계단)엔 walk 정식화(CoM-centering 포함)가 trot보다 낫고(정적 발배치), 오프라인 캐시라 솔버 iteration 넉넉히 써 발판 품질↑ 가능. TO의 값어치 = 발판+접촉스케줄이지 실행가능 base 궤적이 아니다. 평지·관용 gap엔 DTC 끄고 순수 Raibert-RL(P2.7).
