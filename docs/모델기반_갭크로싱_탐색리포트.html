한 줄 결론(갱신 2026-07-27 後반) — "실행이 벽"이던 갭 크로싱을 ★C++ 실시간 TAMOLS를 구현해 넘었다: 정식화(제약5+비용3)·SQP-RTI 솔버를 Drake와 정합 검증하고, 폐루프(WBIC 추종)로 0.20m 갭을 falls=0로 통과(트롯 x=0.62). 관건은 셋: ①실시간 솔버(26ms/5-iter, Drake 583× 극복) ②게이트=진짜 트롯(원본은 페이스라 측방전복) ③base 자세 bounds 조임(과격참조→yaw드리프트 제거). 남은 것 = 완전크로싱(뒷발도 넘기는 더 긴 플랜)·해석Jacobian(<5ms). 모델기반으로 갭 크로싱 가능 실증(이전 "실행 불가" 결론 반증).

1목표와 배경

가정환경 험지(문턱·가구밑 갭)의 핵심 난제 = 불연속 지형(갭)에서 base와 발판을 협조시켜 건너기. A(SRBD-MPC+WBIC)·B(kinodynamic MPC)는 폐루프 보행은 되나 발판만 greedy nudge라 갭 협조가 없음. 모델기반 지형계획기(TO) 계보 — TOWR(Winkler)·TAMOLS(Jenelten)·Perceptive NMPC(Grandia) — 중 TAMOLS(base+발판+타이밍 공동최적화, 지형특징 활용)를 정공법으로 검증.

tamols-rl(ianpedroza, Drake) 정식화에 02_Leg 파라미터(m=37.9·nominal 0.52·μ0.6·sphere발) 적응. GAP=0.20m 갭에서 feasible solve.

3실행(executor) — 세 가지 모델기반 시도, 전부 갭 실패

시도구성접근(평지)갭 크로싱실패 원인
개루프 WBICTAMOLS 궤적 시간재생 + WBIC측방 드리프트✗피드백 없음(개루프의 벽)

핵심 규명 — 문제는 "폐루프냐"가 아니라 "협조냐"다. B 폐루프는 평지 안정(모델기반 폐루프 자체는 됨, RL 불필요). 갭 실패는 base를 갭 너머 발판에 협조 이동시키질 못해서 — heightmap은 발판만 국소 nudge하고 base 계획은 별개. TAMOLS는 그 협조를 하지만 오프라인이라, 실행 시(개루프·greedy) 협조가 깨진다.

최소 horizon(2-phase)조차 2.6 Hz(cold) — 실시간과 19×, warm-start로도 ~4–13 Hz로 50 Hz 미달. Drake(ianpedroza)는 연구·오프라인용이라 per-solve 오버헤드가 큼. 진짜 TAMOLS 실시간은 전용 C++ fast solver(커스텀 QP, Drake 범용 NLP 아님) 덕이며, 실시간화 = 튜닝이 아니라 C++ 재구현(583× 못 메움).

실행 성공의 3요소 — ① 실시간 솔버(C++ SQP-RTI, 583× 극복). ② 게이트=진짜 트롯: 원본 Drake gait([1,0,1,0]/[0,1,0,1])는 좌우쌍 swing = 페이스라 측방 롤 전복(x=0.29). 대각쌍 트롯([0,1,1,0]/[1,0,0,1])으로 측방안정(x=0.68). ③ base 자세 조임: 참조가 roll/pitch ±11°(rp_max 0.20 상한)로 과격→yaw 드리프트(-51°). rp_max 0.06으로 조이니 yaw ±7°·falls=0. 즉 "폐루프 greedy는 base–발판 협조 부재로 갭 실패"를 실시간 TAMOLS(공동최적화)가 실제로 넘었다.
  • 이전 "실행이 벽" 결론 반증 — 모델기반(실시간 TAMOLS)으로 갭 크로싱 falls=0 실증.
  • 남은 것: 완전 크로싱(현 5-phase는 뒷발이 갭 앞 0.40에 남아 base 전진 시 과신장→끝에 base 침하 z0.23. 뒷발도 넘기는 더 긴 다단 플랜 필요) · 해석Jacobian(<20ms 실시간) · WBIC yaw/base-z 홀드 미세튜닝.
  • 온라인 TO(DTC) 최종 — 이 실시간 TAMOLS가 배포서 온라인 플래너(DTC), RL이 추종. 오프라인이면 APT-RL 교사.
결정(갱신) — (a) C++ 실시간 TAMOLS 착수→갭 크로싱 falls=0 달성. 다음 = ①해석Jacobian(실시간 <20ms) ②다단 완전크로싱 플랜 ③A/B 폐루프에 온라인 TO 통합(DTC). RL 실행기는 병행 트랙(APT-RL).
