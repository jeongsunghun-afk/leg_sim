simulation / biped · MPC + WBIC

2족 보행 컨트롤러

quad 17-DOF 뒷다리 2개를 추출해 만든 8-DOF 2족 로봇. 성숙한 Convex-SRBD MPC + 전신 WBIC 스택을 이식하고, 점발(동적 보행)과 평발(정적 서기)을 같은 모델·같은 제어기에서 전환한다.

nv=14 · nu=8 · freejoint MPC 50Hz · WBIC 500Hz C++ (eiquadprog) 배포 통합모델 biped_flatfoot.mjcf

01 무엇인가

모델·알고리즘·통합 구조 한눈에

모델 — quad_real_17dof의 HL/HR 뒷다리만 추출(관절 이름 동일 → C++ 컨트롤러 발참조 그대로 재사용) + 재설계한 최소 몸통(freejoint base, CoM을 고관절 위 정렬). 발 끝에 toe 접촉구, 발목 관절 쪽에 heel 접촉구를 두어 한 모델로 두 접촉 형태를 지원한다.

제어 — Di Carlo(2018) Convex SRBD MPC가 지면반력(GRF)을 계획하고, 전신 단일 QP인 WBIC가 이를 추종하며 CoM·자세·스윙·접촉 제약을 동시에 만족시킨다. 배포는 C++(biped_control.hpp, eiquadprog).

핵심 아이디어
발목을 세우면 toe만 닿아 점발(죽마형, 동적 보행), 눕히면 heel+toe 밑창이 닿아 평발(정적 서기 가능). 적응형 접촉 감지가 "실제 닿은 구"만 골라 쓰므로, 접촉 모드는 모델 교체 없이 런타임 자세로 결정된다.

02 두 접촉 모드

점발과 평발은 물리적으로 상보적이다

1점 · 점발 보행 OK

발목을 세워 발끝 하나로 지지. 발목 토크의 모멘트 팔이 0이라 정적 균형이 원리적으로 불가 → 항상 stepping(event-DCM capture-point)으로 동적 균형.

  • 전진·후진 보행 0.15 m/s, falls=0
  • 정적 서기 불가(항상 스텝)
  • 단일 접촉 → WBIC quadprog 경로

2점 · 평발 정적 OK 보행 WIP

발목을 눕혀 heel+toe 16cm 밑창으로 지지. 밑창이 발목 ZMP를 제공해 전후(pitch) 균형이 가능 → 정적 양발 지지가 성립.

  • 정적 서기 tilt 0.3°, 무한·무표류
  • 동적 보행은 개발 중(아래 §05)
  • 다중 접촉(rank-deficient) → proxqp/정칙화

왜 상보적인가 — 점발은 발목 토크 모멘트=0이라 서지 못하고 걷는다. 평발은 밑창이 pitch를 지지해 서지만, 걸으려면 발목 push-off·heel-toe 롤이 있는 ZMP 보행 게이트가 필요하다. 그래서 현재는 "서려면 2점, 걸으려면 1점"으로 쓰고, GUI로 전환한다.

04 개발 여정

점발 동적 균형에서 평발 통합 아키텍처까지

  • B1 · 점발 정적균형 불가 규명
    점 접촉은 지지점 둘레 모멘트=0 → lean 제어 불가, 대칭 스탠스서 앞으로 토플. "정적 양발"이 애초에 불가능한 목표였음.
  • B2–B3 · 동적 스텝핑 + MPC 통합
    capture-point(ξ=x+v/ω) 제자리 스텝 + Di Carlo SRBD MPC가 수평 균형 GRF 공급. GEARBOX(반사관성) 누락이 초기 발산의 근본원인이었음.
  • event-DCM 게이트 돌파 → 전진 보행
    스텝 착지를 측방 DCM crossing에 동기 → 제자리 균형 0.7→7.9s, 이후 전진 보행 20+s 무낙상. base-frame 발배치로 다리꼬임 해소.
  • 배포 경로 · 추정 · 지연보상 (C++)
    leg-odometry + 접촉높이 z추정으로 폐루프 성립(killer는 z추정이었음), 모델-롤아웃 지연보상. state_estimator.hpp · deploy_loop.hpp.
  • 평발 2점 + 통합 1점/2점 전환
    발링크 양끝 heel+toe 밑창으로 정적 양발지지 달성(점발 B2 해결). 통합모델·런타임 contact_mode. C++ 이식 완료.
  • 평발 동적 보행 (진행 중)
    전후 CoM 규제·발목 flat 고정으로 뒤로 표류 → 전진 전환 달성. 과속·CoM 상승 안정화 튜닝 중.

05 평발 보행 — 진행과 난관

점발 게이트를 평발에 그대로 쓰면 안 되는 이유

평발은 전후와 측방이 다르다. 밑창이 앞뒤 16cm라 발목 ZMP로 전후 균형이 가능하지만, 좌우로는 좁아(~2cm) 측방은 스텝으로만 잡아야 한다. 그래서 게이트를 분리했다.

해결한 근본 원인

  • 발목이 flat서 0으로 서던 문제 → 강고정(FLAT_WANK)으로 밑창 유지
  • 전후 CoM 규제 부재 → CoP가 CoM 앞에 놓여 뒤로 넘어감 → CoM-x 추종 task 추가
  • MPC·WBIC 높이 충돌 → 평발서 MPC 추종 약화(FLAT_WLAM)로 WBIC task 지배

결과: 뒤로 표류(x −0.5) → 전진(x +0.8).

남은 난관

  • 과속 — 명령과 무관하게 ~0.5 m/s로 달림(발목 CoP 속도 규제 부족)
  • CoM_z 상승 — 0.36 → 0.41로 떠올라 ~1.8s 토플
  • 제대로 하려면 ZMP 프리뷰 기반 CoM 궤적 생성(Kajita) 급의 서브시스템 필요

06 기억해둘 기술적 발견

디버깅에서 나온 값진 교훈들

Python vs C++ parity
Python 점발 보행은 모든 mujoco 버전(3.3.6~3.9)·모든 커밋에서 0.1s에 발산하지만, C++ 컨트롤러는 정상 작동한다. 배포·검증은 C++가 기준(run_gui_cpp). 같은 알고리즘의 포팅 불일치.
rank-deficient 접촉
heel+toe가 같은 강체 발에 있어 no-slip 등식이 rank 결손 → eiquadprog 간헐 실패 → 미세 표류 누적 낙상. 정칙화 강화(λ블록 1e-2 · P 1e-6)로 실패 0.1%↓, Python의 proxqp 역할을 대체.
발 메시 충돌
발을 눕히자 collidable 메시가 지면에 파고들어 발산 → 접촉은 구(sphere)로만, 시각 메시는 충돌 off.
폐루프의 killer는 z추정
leg-odometry 위치 적분에서 xy는 수 m 표류해도 무해하지만 z 표류가 WBIC 높이 task를 즉시 붕괴시킨다. z를 적분 대신 접촉으로 직접 측정(base_z = −p_foot_z)하면 드리프트 없이 폐루프 성립.

다음 단계
